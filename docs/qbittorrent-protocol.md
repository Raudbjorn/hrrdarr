# qBittorrent protocol

This provider uses HTTP polling, with operation-scoped authentication. There is no documented qBittorrent WebSocket API in the official specifications used here.

Protocol sources: [qBittorrent 3.2–4.0](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-v3.2.0-v4.0.4)), [4.1–4.6](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1)), [5.x](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-5.0)), and [API-key authentication](https://github.com/qbittorrent/qBittorrent/wiki/API-Key-Authentication-(%E2%89%A5v5.2.0)). Inspected 2026-09-25. These are protocol specifications, not evidence of a live-client run.

Requirements inventory comes from `src/NzbDrone.Core/Download/Clients/QBittorrent/` and `Download/TorrentClientBase.cs` in Sonarr `76c684e097f16ac216e6213845e5cac372774995` and Radarr `c90668a520664ad0c91812cfee57c41928ad2148`. Implementation is independent. The acceptance remains **same client safely processes both media types**; completing these protocol methods does not establish the later download/import automation gate.

## Boundaries

- Reuses the bounded provider transport and its provider/global leases, deadline, body limit, cooldown and redirect refusal. No retry of a mutating request. A lost response, server error, or unverifiable postcondition returns `MutationUnknown`.
- SID cookies remain inside one operation, tied to the configured endpoint. Login requires `Ok.` plus a validated SID; HTTP 200 alone is insufficient. Read requests may reauthenticate once. Up to eight observed SID values are retained only for redaction within the operation, including expired cookies; further session rotation fails closed. API keys use Bearer authentication; absent credentials allow explicitly configured remote authentication bypass. Neither login nor bearer headers are forwarded to torrent-source URLs.
- Modern discovery falls back to legacy only on HTTP 404. Authentication/network errors never trigger fallback. Legacy API versions are normalized from their integer representation. Versions lacking category support are explicitly unsupported because this shared provider requires domain isolation.
- Public pages carry media domain; internal mutations require `MediaTarget::Episode` or `MediaTarget::Movie`. Every hash mutation checks the returned category against that domain's active/imported categories. Literal `all`, hash separators and arbitrary hashes are rejected. Category membership does **not** prove an episode/movie association. The future durable grab journal must bind target to download identity before invoking mutations.
- Remote category checks cannot lock out another qBittorrent user changing categories between requests. The local provider lease serializes only hrrdarr's own operations.
- Category creation is an explicit part of submission. Test only reports missing categories; it does not create them. An explicit imported-category action can move remote files when automatic torrent management is enabled.
- URL submission first retrieves a bounded torrent with no client credentials, validates its original bencoded `info` bytes, and uploads those bytes. It does not blindly ask qBittorrent to fetch an opaque URL. Magnet btih hexadecimal/base32 and btmh SHA256 identities are validated; hybrid identities remain distinct. A v2 identity is matched through exact identity or returned `infohash_v2`, never by guessed truncation.
- Accepted adds return an observed hash only when identity and domain match. Otherwise they return pending identities; a later read must reconcile them. An existing same-domain hash returns `AlreadyPresent`; foreign-domain collisions fail before add.
- File names are bounded relative remote names. Remote paths/properties stay private protocol facts; they do not authorize local filesystem access. Remote path mapping and file import remain separate work.
- Pagination is a live client view, not a snapshot. Exact legacy/v2-identity reconciliation uses a bounded 500-item scan; saturation is an explicit unsupported result, never proof of absence. A future paginated collector must resolve larger libraries within its own durable work budget.


## Versioned mutations and observed results

Protocol gates are checked before category creation or submission. The current adapters use:

| Subfolder layout before API 2.7 | Legacy 1.16+ / modern 2.x | Send `root_folder=true`; omit layout entirely for the Default setting. |

The [official API changelog](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1)#changes) establishes inline tags, share limits and multiple file indexes. Tagged protocol handlers for [4.0.0](https://github.com/qbittorrent/qBittorrent/blob/release-4.0.0/src/webui/webapplication.cpp), [4.3.1](https://github.com/qbittorrent/qBittorrent/blob/release-4.3.1/src/webui/api/torrentscontroller.cpp), [4.3.2](https://github.com/qbittorrent/qBittorrent/blob/release-4.3.2/src/webui/api/torrentscontroller.cpp), and [4.6.0](https://github.com/qbittorrent/qBittorrent/blob/release-4.6.0/src/webui/api/torrentscontroller.cpp) establish the accepted request fields. These source observations establish contracts, not runtime compatibility.

Control success requires observed state: force-start boolean, requested file priorities, raw share limits, or the requested queue edge. Bottom priority uses a bounded one-row global descending-priority read; it never mutates that other torrent. Missing, contradictory or malformed post-mutation facts remain `MutationUnknown`. Imported-category moves require coherent completion (complete state, progress and any supplied remaining-byte count), not an upload-state label alone. Submission verifies observed sequential/first-last options and requested share limits; priority/force follow-ups use the same checks. Requested tag subsets are also verified on a fresh scoped read. Layout effects and delayed client application are not inferred from an HTTP 200 response.

## Legacy API 7–13 scope and submission

The [3.3.1/API 7](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.1/src/webui/webapplication.cpp) and [3.3.4/API 9](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.4/src/webui/webapplication.cpp) handlers use `label` for add/query, `labels` in sync, and `setLabel` for imported-scope changes. [3.3.5/API 10](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.5/src/webui/webapplication.cpp) changes these to category/categories/setCategory and provides addCategory; [3.3.12/API 13](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.12/src/webui/webapplication.cpp) still lacks an atomic paused add parameter. Shared negotiated-scope helpers cover query, sync, identity checks, item parsing and mutations. A missing authoritative field or contradictory extra scope field fails validation; modern rows cannot fall back to legacy labels.

Old labels are assigned with the scoped add/setLabel operation; there is no invented create-label call. Unsupported filesystem-style label names fail before mutation. Default-layout magnet/multipart submissions omit ignored paused/sequence fields. Stopped requests before API 14 are rejected before side effects. Started requests are permitted only with an observed running result: the [old session implementation](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.1/src/base/bittorrent/session.cpp) consults a global paused default which its preferences endpoint does not expose. hrrdarr cannot preflight that hidden default; a paused outcome is `MutationUnknown`, without resume, pause or add replay. Forced/priority follow-ups remain bounded scoped actions with observed effects.

Owned fixtures cover API 7/9 label and API 10/13 category wire forms, both domains and payloads, missing registry entries, query filtering, imported-scope moves, forced/priority observations, hidden paused outcomes, lost responses, foreign scope and invalid old labels. Fixtures use negotiated legacy fields rather than modern aliases. Legacy connection/status checks and seed provenance use the source-bounded profiles described below; submission evidence alone still does not establish full legacy provider compatibility.

## Legacy API 14/15 submission

Tagged handlers for [3.3.13/API 14](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.13/src/webui/webapplication.cpp) and [3.3.16/API 15](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.16/src/webui/webapplication.cpp) accept category and `paused` for both URL/magnet and multipart upload. They do not consume `root_folder`, sequential or first/last inline fields. This source evidence takes precedence over broader wiki introduction-version descriptions. The adapter sends only supported fields; requested layouts/sequence/first-last features remain explicitly unsupported before category creation or submission. A stopped add is atomic at the protocol boundary, never emulated by starting and then pausing.

Their [legacy list serializer](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.13/src/webui/btjson.cpp) exposes `seq_dl`, `force_start`, category and priority; `f_l_piece_prio` is conditional on metadata. The same observed postconditions remain mandatory. Started submissions now reuse the resume running-state predicate across legacy and modern adapters; paused, stopped, unknown/error and transitional states lacking proof remain ambiguous rather than successful. Missing metadata-dependent facts yield `MutationUnknown`, not invented false values. Force/first-priority follow-ups retain scoped prechecks and observed effects. Upload may succeed with an empty response body. API 14/15 fixtures omit modern alias/tag/content-path/time-limit fields and represent legacy resolved ratio limits separately from modern raw inheritance semantics.

Owned fixtures cover both domains, magnet and multipart, Started/Stopped/Forced states and priority follow-ups, unsupported-option preflight, ignored started/stopped intent, foreign scope, missing metadata facts and a lost add response without resubmission. This closes the API 14/15 default-layout submission subset only; older optional behavior and metadata/follow-up recovery remain explicit work. No live-client run is claimed.

## TV tag application

The [official API changelog](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1)#changes) establishes `addTags` at API 2.3 and the inline add field at 2.6.2. For older supported tag clients, submission first observes the derived identity, rechecks its category, and issues one additive `addTags` request for the actual API ID. No global tag deletion or replacement is used. Newer clients receive the tags with the original add request. Both paths require the requested subset on a final freshly scoped torrent read; missing, malformed, ignored or unverifiable results yield `MutationUnknown`, without repeating add or tags. Unrelated existing tags are permitted and preserved by the additive contract.

Prepared tags reject empty, leading/trailing whitespace, commas, controls and duplicate values. Internal whitespace is preserved; the bounded comma-separated response parser trims separator whitespace before exact membership comparison. Movie scopes send no tags even if per-release tag inputs are present. `AlreadyPresent` remains read-only and does not apply tags to an existing torrent or claim tag completion. `Pending` and lost responses still require caller-owned durable follow-up recovery; presence reconciliation alone does not prove tags were applied. Category checks cannot eliminate an external actor's concurrent changes.

Owned fixtures cover magnet and multipart requests at API 2.2.1, 2.3.0, 2.6.1 and 2.6.2, additive preservation of external tags, absent/null/malformed tag observations, ignored effects, foreign-category changes, movie isolation and existing-torrent nonmutation. No live-client or durable recovery equivalence is claimed.

## Remote torrent identity

Prepared infohashes and the client's returned `hash` have different roles. On API 2.8.4+, identity resolution performs a bounded unfiltered scan even for v1-only input: a hybrid can expose a v1 alias while using a different API torrent ID. The [4.4.0 serializer](https://github.com/qbittorrent/qBittorrent/blob/release-4.4.0/src/webui/api/serialize/serialize_torrent.cpp) exposes `hash`, `infohash_v1` and `infohash_v2`; its [API declaration](https://github.com/qbittorrent/qBittorrent/blob/release-4.4.0/src/webui/webapplication.h) establishes the boundary. This is protocol evidence, not copied implementation.

Aliases must be correctly typed hexadecimal hashes of their respective lengths. An empty string advertises an unused hash kind; an omitted field cannot establish a complete alias search. Both-empty aliases, duplicate torrent IDs/aliases, contradictory hybrid mappings, and identities split across rows fail explicitly. Foreign-category matches remain scope conflicts. An API-ID collision with contradictory aliases cannot authorize submission. A 500-row scan is insufficient evidence, even if a candidate was seen, and fails explicitly. Every requested hybrid identity must agree on one row. Full v2 aliases establish the mapping to the returned API ID; the provider never guesses an ID by truncation. Reconciliation uses the same v2 version boundary as submission.

Controls, files and details consume the observed API ID and recheck its category; they do not reinterpret a supplied ID as an infohash alias or prove durable target ownership. Owned TV/movie fixtures cover pure v2, hybrid, v1-only hybrid lookup, case normalization, malformed/missing/empty aliases, split identities, duplicates, scope/API-ID collisions, saturation and API 2.8.3/2.8.4. Accepted-but-delayed and applied-but-HTTP-502 cases reconcile later without another submission. Missing fields on purportedly modern clients conservatively remain unsupported; no live-client equivalence or unbounded collector is claimed.

## Private client status

`client_status` reads a domain's predicted remote root, root source, endpoint locality and completed-download removal hazard. It starts with preferences `save_path`; modern clients may override it with the exact active category's nonblank `savePath`. An absolute path replaces the default; a relative path joins it. Legacy categories, missing categories/paths and blank category paths retain the default. Imported categories and parent-category inheritance never participate. API 2.0 array, 2.1.0 sync object and 2.1.1 categories-endpoint fixtures cover both domains.

Remote paths are bounded lexical facts, independent of hrrdarr's host OS. POSIX, Windows drive roots and UNC roots are accepted; `//server/share` remains an absolute UNC spelling with its leading double slash preserved, and backslash UNC spelling is likewise preserved. Relative components use the default's separator style. Drive-relative/device paths, dot traversal, malformed UNC, control characters and overlong paths fail explicitly. These conservative limits do not assert that all remote filesystem names are supported.

Literal loopback IPs and the normalized `localhost` endpoint label yield `Loopback`; other hosts remain `Unknown` without DNS or interface discovery. This fact cannot establish shared mounts, filesystem access, or the destination behind a proxy. The removal hazard reuses the exact connection-test predicate but is reported instead of rejected. Missing/malformed required preferences fail explicitly. Status has no public DTO/serialization or Debug path exposure and never reads or changes local files. Its predicted category root does not replace a torrent's actual save/content path, including when automatic torrent management is disabled. Path mapping and import authorization remain separate work.

## Seed facts and retention

Internal `TorrentDetails.seed_policy` keeps raw and resolved ratio, seeding-minute and inactive-minute limits separate. `-2` inherits only an enabled global limit; `-1` disables that axis; zero is an active threshold. Missing facts remain unknown and malformed supplied facts fail validation. The pure evaluator takes an observation clock: ratio uses a 0.001 tolerance, elapsed seeding uses `>=` minutes converted to seconds, and inactivity uses strict `>` with future/zero/missing activity timestamps unknown. The axes combine with three-valued OR. Readiness additionally requires coherent completion and `pausedUP`/`stoppedUP`; it never authorizes removal or an imported-category move.

Absent list `seeding_time` falls back to the already scoped properties response. Property reads failing propagate an error; missing properties time and its `-1` sentinel remain unknown. Negative supplied list time retains the public response validator's explicit rejection. Missing legacy per-torrent ratio facts remain unknown; global configuration does not prove that a hidden per-torrent override is inherited. `client_removes_on_limit` reports only the configured action, even when global limits are disabled, and does not assert an active destructive policy.

Connection tests separately reject the reference retention hazard: removal/delete action plus either enabled global ratio or enabled global seeding time below 20,160 minutes. An enabled time setting with raw `-1` also fails this retention guard, matching the references’ signed threshold comparison; per-torrent seed-policy sentinel resolution remains separate. Required flags/action and an enabled missing time limit fail validation; no inactive-time extension is inferred. This is a read-only configuration check. Wire fields and time units follow the [official preferences and torrent API](https://github.com/qbittorrent/qBittorrent/wiki/WebUI-API-(qBittorrent-4.1)); the readiness/retention predicates are requirements inventoried independently in both pinned clients.

## Legacy seed provenance

Known legacy API 6–17 profiles distinguish unavailable features from missing observations. [3.3.16/API 15 preferences](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.16/src/webui/prefjson.cpp) lacks the seeding-time feature; [4.0.0/API 16 preferences](https://github.com/qbittorrent/qBittorrent/blob/release-4.0.0/src/webui/prefjson.cpp) and [4.0.4/API 17 preferences](https://github.com/qbittorrent/qBittorrent/blob/release-4.0.4/src/webui/prefjson.cpp) expose global seeding-time flags and minutes. Thus API 6–15 time axes are `Unavailable`, while API 16/17 retention checks require the actual time preferences. Inactive limits are unavailable across these legacy profiles. Unsupported supplied fields are rejected consistently in connection tests, status and detail facts. Future/unrecognized legacy versions do not inherit an absence exemption; modern required-field validation is unchanged.

Legacy `ratio_limit`, when supplied, is an observed **effective** value, as shown by the [legacy serializer](https://github.com/qbittorrent/qBittorrent/blob/release-4.0.4/src/webui/btjson.cpp) calling `maxRatio`, which [resolves global inheritance internally](https://github.com/qbittorrent/qBittorrent/blob/release-3.3.16/src/base/bittorrent/torrenthandle.cpp). Its raw value stays `Unknown`, with `ObservedEffective` provenance. Absent fields remain `Unknown`; the global ratio is never substituted. API 16/17 has hidden per-torrent time overrides but does not expose their limit in the list response, so its effective time axis remains unknown even with known global preferences. Unavailable axes cannot themselves be reached and do not invent disabled raw wire values.

Owned API 7, 10, 15, 16 and 17 fixtures cover both domains through test/status/details using actual absent/present legacy preference fields, ratio-removal rejection, properties elapsed-time fallback, effective ratio differing from the global setting, unknown missing ratios and invalid supplied facts. Pure tests cover the full known profile range and future-profile nonexemption. The API 16 time boundary corrects an earlier research assertion that all legacy preferences lacked time limits. No assumed-inheritance readiness, deletion authorization, live-client equivalence or cleanup orchestration is introduced.

Its successful reauthentication response reflects both old and new SIDs plus username/password; all are absent from public output. Request path/count assertions exclude mutation, legacy fallback and extra retry. This is owned-fixture response evidence, not a live-client run or process-log capture.

Persisted initial state/layout/sequential/first-last/TV-tag settings drive submission; per-release tags and share limits remain method inputs. The protocol handoff is explicit:

1. `prepare` validates the target/options and derives identities from the retained magnet or exact torrent bytes. URL retrieval happens here, without contacting qBittorrent. It returns an immutable, non-cloneable `PreparedDownload`.
2. The caller records `prepared.identity()` **before** submission, alongside its provider UUID/revision, settings snapshot, recent/older priority intent, per-release options and durable operation state. The serializable record contains the typed target, validated hashes, payload SHA256 and a fingerprint of all provider settings, including endpoint URL/base and active/imported categories. It excludes the source URL, torrent bytes and credentials. The full settings fingerprint fails closed even after unrelated scope edits; recovery must retain the original snapshot or explicitly resolve drift, never silently reconcile against a different configuration.
3. `submit` consumes the prepared payload and rejects settings drift before contacting the client. It uses retained bytes; it never fetches the source URL again. Consumption prevents reusing that value, but cannot prove journal persistence or prevent a caller preparing a second value.
4. `reconcile` accepts a reloaded identity, validates its bounds and settings binding before I/O, and reads remote identity/category facts. `Observed` proves presence in the expected domain only; it does not prove ownership by this particular target or completion of priority/force/share-limit follow-ups. `NotObserved` is an observation at one instant, **not** proof that submission failed or authorization to submit again.

The old combined `add` entry point is removed. `Pending` may return before follow-ups execute; `MutationUnknown` may occur after any external step. A later durable workflow must record/recover these steps without blindly retrying add. The protocol record is not a durable queue, a tamper-proof record, or a database commit receipt. Provider UUID/revision ownership, cancellation/restart recovery, protected payload retention and any restoration of a submission remain caller obligations; the in-memory prepared payload itself is not serialized.

## Download diagnostics and imported categories

The public download item carries an optional static `diagnostic` enum, never a client-provided error message or state string. Recoverable error, missing-file and stalled states report `warning`. Metadata requests read DHT preferences once per page; an observed false reports `dht_disabled`, while true or an absent field retains queued `metadata`. Missing DHT is unknown, not an invented disabled/default-enabled setting. Malformed supplied fields or preference documents fail explicitly. Details reuse their existing preferences read; completion-only controls need no DHT read. Unknown remote states retain native `unknown` with a static diagnostic.

ETA is zero only for coherent completion. The client's unknown sentinel8640000, negative/malformed values and values above365days remain null. A category move provisions the configured imported category only after confirming target scope and completion, then rechecks both immediately before moving. Failed or ambiguous provisioning never proceeds to setCategory; an observed category creation may remain if a later scope/completion check fails. Category changes may move remote files under automatic torrent management, and cannot lock out external actors. No operation automatically retries a mutation.
