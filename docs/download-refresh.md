# Durable download refresh

`refresh_downloads` is the first executable durable command. Its target is an explicit provider UUID and `tv` or `movies`, plus the expected provider revision. It reads the configured active qBittorrent category. It does not submit, remove, import or associate downloads. Identical hashes or titles in different categories remain separate, explicitly unassociated observations.

## API

All routes use `/api/v1`. Requests reject unknown fields/query flags. Commands require a locally owned database; existing remote deployments still serve their other APIs with the command worker disabled.

- `POST /commands`: `CommandInput` with name `refresh_downloads`, target, provider revision and `normal`/`high` priority. Returns 202 and the command. An existing active command for the same provider/domain/revision is returned unchanged; a different active revision conflicts. Terminal commands do not deduplicate a new explicit request.
- `GET /commands`: optional media/status filters, limit 1–100 (default 50), offset 0–1024. Returns total and deterministic newest-first history. `GET /commands/{uuid}` returns one command.
- `POST /commands/{uuid}/cancel`: atomically cancels queued, waiting or running work; terminal work remains unchanged. `DELETE /commands/{uuid}` explicitly deletes terminal history only. No client download or media is deleted.
- `PUT /download-refresh/schedules`: `RefreshScheduleInput` with target, required nullable revision (`null` creates), provider revision, enabled flag and interval 60–86400 seconds. Configuration updates require the returned revision. Enabled schedules become due immediately. GET returns the bounded, ordered schedule list; DELETE accepts target and revision.
- `GET /queue`: required provider UUID/media type, limit 1–100 and offset 0–1000. Returns the latest successful snapshot, observation time, provider revision, nullable originating command UUID, total and items. Each item contains `association: null` and the real `DownloadItem` DTO. No snapshot is 404, distinct from a successful empty observation.

Errors use the shared static error envelope: malformed input 400, absent command/snapshot 404, stale configuration or active-history deletion 409, capacity admission 429, unavailable local ownership 503, and storage faults 500. Response bodies are capped at 1 MiB; request bodies at 8 KiB. Durable failures expose static codes and timestamps, never transport URLs, credential bundles or raw remote errors. Command IDs correlate structured settlement logs with status/error and domain. Progress is state, attempt count and timestamps; `items_observed` is the completed successful count, not a fabricated percentage.

## Execution and recovery

One runtime owns each local database, backed by the existing lifetime file lock and a guard rejecting a second runtime for the same database object. Production shares the provider router's pooled transport and per-provider admission lanes with refresh. A single worker checks due schedules/commands every second, orders high priority first and then oldest command/UUID, and performs no database transaction across HTTP. Blocking a probe does not hold a database write transaction.

Claiming increments attempts once. States are queued → running → succeeded, failed or retry_wait; active states may become cancelled. At most three attempts are permitted. Retry delays use exponential backoff with bounded jitter and respect a transport Retry-After up to one day. Restart recovers interrupted running reads without resetting attempts, terminalizing exhausted work. Obsolete queued/waiting provider revisions fail independently of their future retry time, freeing the scope on the next worker pass. Retry is safe here because this concrete consumer only reads downloads; this is not a replay policy for future grabs/imports.

Cancellation drops the in-flight read when observed; publication rechecks command state and provider revision inside the final transaction. Shutdown aborts and awaits the worker so ownership and transport permits remain held until the actual future is dropped. Default process termination may leave a running row for startup recovery. Provider edits invalidate snapshots and visibly disable retained schedules with `provider_changed`; schedules must be explicitly reconfigured using current revisions. Explicit provider deletion removes its schedule/snapshot but preserves command history.

Each refresh shares one HTTP operation and session across pages, with a 30-second operation deadline, five-second preflight, 500-item pages, at most 1000 distinct hashes and 1 MiB serialized items. Exactly 1000 items requires an empty terminator page. Duplicate hashes, invalid pages or over-limit responses fail rather than truncate. Auth-session redaction persists across all pages. Remote paging is not atomic: a successful dated snapshot is an observation, never proof of absence or authorization to remove/import anything.

Success and replacement of the latest snapshot commit together. Failed or cancelled refreshes retain the prior dated success unless provider configuration invalidates it. Deleting a terminal originating command only nulls the snapshot's receipt pointer. If cancelled history is deleted before the running read observes cancellation, both cancellation checks and final publication treat its absence as terminal; they neither publish nor report a storage failure. Storage caps are 1024 active (queued, running or retry-waiting) commands shared across the whole command pool, 64 schedules and 64 latest snapshots (each at most 1 MiB). Completing, failing or cancelling a command frees its own slot in that cap immediately; the underlying command rows themselves are never implicitly pruned, so a table's stored history can still grow without bound over a long uptime even though it no longer blocks new admissions. A saturated *active* pool rejects manual admission and records `command_history_full` on due schedules; explicit terminal-history deletion still exists but now only trims stored history rather than being required to free admission capacity. A due schedule advances once to now + interval, coalesces an existing active scope command and does not replay every missed interval. `last_run_at` records accepted enqueue/coalescing, not successful completion.

Migration 0016 enforces immutable command identity, allowed transitions, attempt counts, active scope uniqueness, current-provider admission, scoped snapshot identity and storage caps. Snapshot creation requires a succeeded matching command; all unknown client items remain without library associations.

## Evidence and limits

`tests/commands_api.rs` exercises real owned HTTP endpoints and scratch databases: both media domains with identical hash/title, priority, shared transport exclusion, deduplication, progress, previous-success retention, retries, active cancellation, close/reopen recovery, exhausted attempts, future stale retry invalidation, schedule restart/deduplication, capacity failure/recovery and explicit deletion. A separate-process regression starts the actual worker, rejects a competing database opener before it can recover or probe, forcibly kills the first process during a real blocked HTTP read, and reopens in another process. Both domains retain the same command UUID/target, resume at attempt two, publish only into their own scope, and make only GET download requests. No running rows are fabricated by the fixture. `commands::worker::tests::cancelled_deleted_history_is_terminal_during_probe_and_publication` failed before the disappearance handling fix and passed afterward; it invokes the real cancel/delete handlers during a blocked read and checks both worker completion paths with no snapshot creation. Protocol tests cover multi-page bounds and cross-page authentication-secret redaction; migration tests cover actual version-15 upgrades, rollback and relational/state constraints.

The initial [Activity UI](activity-ui.md) has separate real-browser evidence for scoped refresh, retry/error display, cancellation and schedules. Local ownership is advisory and cooperative: the process test does not cover hostile database-file replacement or non-cooperating direct writers. No live qBittorrent instance, real credentials, production database/media, power-loss/filesystem corruption or remote worker topology was tested. Authentication may create remote sessions even though download operations are reads. Full tracked-download matching, imported-category processing, completion/failure actions, automatic imports, all other commands, cron scheduling, maintenance, RSS and full Activity/settings UI remain incomplete. New state is the three bounded migration-0016 tables; no dependency is added. None of this establishes the full command, queue or automation parity gate.
