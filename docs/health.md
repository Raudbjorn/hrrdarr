# Native health engine

Health checks share the existing single, locally owned command worker. Cached observations are persisted separately from processing authority. A health warning never disables completed-download handling. The initial registry contains only TV and movie `completed_download_handling` checks; see [detector behavior and transport limits](health-detectors.md). Other health catalog entries and notification delivery remain incomplete.

`GET /api/v1/health` reads a transactionally consistent cached snapshot, without client/network probes. `scope` accepts `all`, `tv`, `movies`, or `system`; `limit` is 1–16 (default 16), `offset` 0–127. Check states distinguish never evaluated, pending, running, stale, failed, and current observations. The summary covers the entire requested scope, independently of pagination. An empty issues page therefore does not assert that checks succeeded. Coverage describes only registered identities. Previously observed issues remain visible during failed or pending rechecks.

`POST /api/v1/health/commands` requires `{ "scope": "all", "priority": "normal" }` (or priority `high`), rejects unknown fields, and returns 202. The response distinguishes a new queued batch, union into an unclaimed batch, and pending selection tokens behind a running/retrying batch. Tokens identify the requested generations; a running command ID does not promise coverage of a later request. Unregistered scopes return 409. One global active health batch participates in the shared 1,024-active-command pool; no fictitious media ID is assigned. A manual admission rejected for capacity rolls back its markers. Automatic markers remain durable for later admission.

`GET /api/v1/health/commands` supports scope, status, limit (default 20, max 100), and offset (max 128). Scope matches membership, including coalesced multi-domain batches. `GET /api/v1/health/commands/{uuid}` returns the full bounded membership. `POST /api/v1/health/commands/{uuid}/cancel` accepts an empty body/query and cancels the **whole batch**, including coalesced requests. Cancellation preserves observations and newer generations. Repeating cancellation on a retained terminal command is idempotent. The newest 128 terminal commands are retained; an unknown or pruned ID is 404, never implied success. Retained history pagination can drift as history is pruned.

Startup starts a new persisted epoch and marks startup checks immediately due. A six-hour schedule survives restart. Configuration mutations persist dirty generations in the same transaction as authority changes, including equal-value explicit CDH saves and download-client create/update/delete/import/bulk changes. Configuration-only work uses a five-second trailing debounce; manual/startup/scheduled/grace work is never postponed by a later configuration change. A queued batch may gain membership; retries retain their original membership and three-attempt budget while capturing fresh generations.

Selected evaluations run outside writer transactions, with a 30-second whole-batch deadline and 250 ms cancellation polling. Publication atomically verifies command ID, running status, attempt, epoch, and every selected generation. Stale inputs publish nothing and preserve newer work. Failures/timeouts retain previous observations. Existing 45-second worker timeout/error recovery also recovers health work. No detector tasks are detached.

Initial failures are visible immediately. For the first 15 minutes, issue/restored transitions are marked in-grace. At the deadline, one durable full-startup recheck must succeed before grace expires. It first applies results while still in-grace, then announces every remaining cached issue once outside grace. A restored transition contains the latest **previous issue** payload. Repeated or changed failures update observations without repeated issue transitions. An exhausted/cancelled grace run schedules another attempt after 60 seconds. Old-epoch grace work cannot expire a new process's grace. This timed, persisted lifecycle is a native adaptation of upstream event-driven grace handling.

`GET /api/v1/health/transitions?after_sequence=0&limit=16` exposes the newest 1,024 diagnostic transitions using monotonic safe-integer sequence IDs. It returns oldest/latest retained sequence, next cursor, and an explicit retention-gap flag. Sequence exhaustion fails publication transactionally; it never wraps. Automatic generation exhaustion records `health_invariant` in the lifecycle without blocking unrelated commands in the shared worker; manual/configuration mutations fail rather than wrap or commit an unmarked change. Responses are bounded to 1 MiB. This journal is **not an acknowledged delivery outbox**: no script, email, webhook, notification routing, provider retry, or external exactly-once delivery is claimed. A delivery consumer must establish its own durable ownership before relying on retention.

Focused evidence lives in `src/health/tests.rs` and `tests/health_engine.rs`: deterministic lifecycle/capacity/fencing/grace/recovery checks, bounded real HTTP probes, and real API plus owned-worker flows. Tests use temporary databases and owned loopback peers only. Full integration verification and UI consumption are separate; no live-provider or performance equivalence is claimed.
