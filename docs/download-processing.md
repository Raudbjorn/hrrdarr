# Owned completed-download processing

Native processing is opt-in per qBittorrent provider and media domain. `GET/PUT /api/v1/download-processing/policies/{provider_id}/{media_type}` reads or changes enabled/copy-or-hardlink policy with a revision compare-and-swap. Missing policies are disabled. Sources remain available for seeding; this workflow never removes client downloads, changes their category, or moves source bytes.

A successful download refresh enqueues completed observations only when they match a trusted RSS receipt's exact client UUID, revision, domain and returned remote torrent ID. Unassociated, pre-existing and uncertain submissions cannot import. `POST /api/v1/download-processing` admits up to 100 unique receipt UUIDs atomically. It accepts the captured provider revision, domain and receipt IDs; repeated requests retain the same receipt and operation.

The shared worker obtains fresh scoped torrent details and validates selected completed files. A filename must match the receipt's current singleton episode or movie title/year and pass the current quality profile, size and upgrade rules. Multiple acceptable files are an explicit ambiguity, not an instruction to choose the largest. Singleton standard/daily/absolute TV and movie files are supported; packs and remaining scene-source/alias workflows remain explicit limitations. This is filename and file-identity assessment, not codec or media-content probing.

Every source requires an explicit host/domain path mapping. The validated basename is preserved under the target library root; unsupported destination collisions fail visibly. The importer rechecks current target, root, profile, policy and mapping before creating one durable operation and immutable receipt link. Network reads and file transfers occur outside database transactions. Cancellation is permitted only before this link exists.

`GET /api/v1/download-processing` supports provider/domain/status/receipt filters, a maximum 100-row page and offset 10000. Detail and cancellation use the receipt UUID. Rows expose typed targets, preflight round and lifetime attempts, static errors/reasons, operation phase and retained original-file recovery state. Requests have a five-second deadline and bounded bodies/responses. A timed-out write has an uncertain outcome: read the receipt before retrying.

Preflight reads retry at most three times per explicitly authorized round. Explicit retry of an unlinked blocked/cancelled row resets only the round count, preserving lifetime attempts. Interrupted linked imports always retain their operation identity. Long transfers run under the existing import lease and consume no additional preflight attempts. A durable import failure parks the row. Explicit resume records `resume_requested`; after acquiring the lease the importer atomically consumes it and clears the prior errors before starting. Duplicate requests while healthy work is active do not grant a later retry. Linked recovery remains possible after automation is disabled or provider configuration changes.

Replacement stages a fresh destination, commits association, quality facts and history atomically, then retains the old bytes as a recovery artifact (or retains a still-shared TV file). Processing becomes imported only after that operation completes. A completed linked history releases the target for a later valid upgrade; original hash claims and submission receipts remain retained. Native unified History records import facts, not a fabricated client removal or seeding-complete event.

Full completed-download handling remains partial: other clients, advanced numbering and packs, comprehensive naming, failed-download replacement/blocklisting, client removal and all upstream monitoring behaviors remain required. The deprecated upstream check-finished command and monitored-processing inventory are requirements references, not claims of runtime parity.

See [manual import recovery](manual-import.md) for descriptor checks, the failed-operation latch, retained artifacts and the explicit recovery limitation around interruption before a retirement-directory checkpoint.

## Focused evidence

`tests/download_processing.rs` uses owned metadata/indexer/qBittorrent HTTP fixtures and scratch media. Real metadata Add creates equal numeric TV/movie IDs; RSS produces trusted receipts, completed refresh admits them, and copy/hardlink imports produce native history. The fixture exhausts exactly three transient detail-read failures without an import intent, then rejects wrong episode/year and multiple eligible files before intent, retains lifetime attempt counts across explicit retries, and ignores sample files. It follows both actual RSS upgrades through a late history-commit failure, parks both at publication, disables processing policies, shuts down the worker/API and releases all database handles before reopening. Explicit recovery retains the same operation IDs. It then fails retirement checkpoint persistence after the originals have been renamed, reopens both committed operations and resumes their existing cleanup. These are controlled checkpoint failures and orderly backend restarts, not abrupt process termination or power-loss tests. Assertions cover original association/bytes on failure, retained recovery bytes after success, hardlink inode identity, stable movie file ID, immutable hash claims and reopening the database without a second submission or import fact.

`search::downloaded::tests::downloaded_files_require_exact_target_quality_and_size` covers exact filename targeting, sample rejection, profile allow-list, size bounds, basename extraction and existing cutoff files. The existing release decision suite checks that the extracted shared quality evaluator retains its prior search behavior. These fixtures do not establish real-client compatibility, media codec validation, every filesystem or failure timing, or full automation parity.

Revision evidence is distinct from the settings revision counter. Newly parsed release observations store `{version, real, is_repack}` with their parser version. A marked downloaded filename must agree with that observation, including repack identity. An unmarked filename can inherit a frozen release observation because renaming may remove markers. Historical receipts without revision observations stay unknown; their titles are never reparsed to fabricate baseline facts. An unmarked file with such a receipt is blocked with `revision_unknown` before an owned journal is created. A retry requires independently observed revision evidence, such as an actual marked filename.

New owned provenance records the release/filename reconciliation and actual revision. Existing owned journals keep their validated factual revision; newly recognized contradictory filename markers stop uncommitted recovery without rewriting receipts, facts or sources. Current policy is rechecked before publication/commit using the durable RSS versus user-search origin. The explicit-search proper-age exception does not exempt repack group or anime group requirements. Completed retirement is not rejudged.

Explicit manual mapping retains its override semantics. Recognized filename revision markers are recorded; unmarked filenames remain unknown rather than acquiring an invented baseline. Existing snapshot null revisions likewise remain unknown. Factual revision drives Quality Full naming, while Quality Title remains the configured quality name.
